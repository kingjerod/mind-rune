# Rulings of the plan 6 run (attachments)

Plan: `docs/superpowers/plans/2026-11-16-attachments.md`. Jerod approved it on 2026-11-16 ("Yes, build it") and asked for it to be built by subagents, each on Opus 5.5 at high effort or better, on its own branch, without pushing. While it ran, the controller decided what the plan and the spec left open, so that the run did not wait. Each ruling says what it costs if it was wrong. Nothing here was seen by Jerod before it was built, but for the plan's decision 15 ("Keep text first").

The branch is `plan-6-attachments`, cut from `main` at `3744b76`. At the end of the plan's own run (25 commits of code and tests) `cargo test --workspace` gave 1181 passed; after the addition of sent pictures (rulings 35 to 43) it gives 1215 passed, 0 failed, 2 ignored, with `cargo fmt --all --check` and `cargo clippy --workspace --all-targets` clean. Jerod ran the live test themself on 2026-11-16, before that addition: it passed.

## Before the first task

1. **Task 6 may touch the window just enough to compile.** The plan's file list for it left the window out, though the queue's type and `push_user` change under it. If wrong: nothing; Task 8 owns the behaviour.
2. **A scene's chips get thumbnails made in code.** The plan did not say how a scene shows a thumbnail without a backend. If wrong: a scene's chip shows the photo sign.
3. **A reviewer read its diff while the next implementer worked**, where the two tasks shared no file. From Task 4 on also where the next task used the one under review, because the plan fixes the interface between them. Fix rounds waited for the running implementer. If wrong: a fix lands a task later.

## While the tasks ran

4. **A line break in a path means `\n` or `\r`.** Such a path, and one that is not UTF-8, reads "Its name cannot be sent". If wrong: one character class.
5. **An image of more than 64 million pixels reads "Too large to send" and is not decoded** (`MAX_PIXELS`, the controller's addition), and so does one the decoder refuses for its size. A small file that unpacks huge can then not eat memory. A photo larger than that cannot be attached as an image. If wrong: one constant.
6. **A failed encode reads "Cannot be read"**, not "Too large to send". If wrong: wording.
7. **The noise test of `attach.rs` takes about 7 seconds** in a debug build and stands; it is the plan's own case. If wrong: an optimisation level for the `image` crate in the dev profile.
8. **A process the program started that inherited its input can keep the writer thread blocked** after the program is killed. Left: one idle, detached thread; the code before hung the caller in the same case. If wrong: the input opened so that children do not inherit it.
9. **"Continue here" and "Continue as a copy" act as "Cancel" when nothing is left to send.** The user can remove every chip of a message without text while the "open elsewhere" question waits. If wrong: one condition.
10. **A session that takes no message takes no chips from a paste**, and the paste falls through as text: an ended session, one with a question waiting, one whose check in the store runs. If wrong: one condition.
11. **White space beside a pasted image is not text.** The image becomes a chip. The plan said "text that is not empty". If wrong: one `trim`.
12. **A press on the attach button while its file dialog is open does nothing**, and any answer of the dialog takes that session's error line away. Before, a double press left a red line that stayed. If wrong: a few lines.
13. **While the "open elsewhere" question shows, a tile keeps the question at its top and cuts the input box.** The session takes no message then, so the box is of no use. Task 10 as first built cut the question's buttons off in the shortest tile. If wrong: a compact card.
14. **In the lowest tile with a queued message and chips, the queued strip and its "Edit" are cut off.** The plan's own rule ("cut off at the top of the box"). Put to Jerod. If wrong: the chips row gives way before the strip.

## The whole-branch review and its fix wave

The review found nothing critical, two Important things and fifteen Minor. One fix wave followed, a scoped re-review found every item addressed, and one small correction came after it (ruling 16).

15. **Preparing an attachment has a thread of its own, and a panic there costs one chip** (Important 1). The plan put preparing on the library thread; a decoder that panicked on a file would have ended that thread for the run, silently, and with it history, the listing and the waking of resting sessions. If wrong: nothing; one more idle thread.
16. **PNG or JPEG is decided by the pixels, and lossless is tried first** (Important 2, then the re-review). An image counts as transparent only when some pixel is. An image over the limits with real transparency goes as PNG and is halved if it must be. An opaque one is tried as PNG at the fitted size, which keeps a screenshot sharp, and goes as JPEG at quality 85 only when that PNG is too heavy, as a photo's is. The plan's decision 6 chose by the alpha channel, which every pasted image has, so a large pasted photo was sent at a quarter of its pixels. The fix wave first made every opaque image a JPEG; the re-review showed that gained nothing for screenshots, and the controller corrected its own ruling. This was a second, small round after the one fix wave. If wrong: one condition.
17. **A JPEG with an orientation tag is always sent upright**, also within the limits, encoded again at quality 90. Every other image within the limits still goes out byte for byte. This withdraws an earlier ruling (byte for byte with its tag): the chip showed an upright picture while Claude would have got it unturned. If wrong: a slight loss on small tagged photos; one condition.
18. **The orientation tag is read for JPEG only.** Reading a WebP's asks for as much memory as the file claims, up to about 4 GiB, and where the system refuses that the app aborts. A tagged WebP or PNG is taken as upright. If wrong: a tagged WebP shows turned.
19. **The attach button and a chip's remove control are Tab stops, built as the send button is.** This withdraws an earlier ruling that they are not. Space presses a focused one (Enter goes to the box's default button at this Rune). As with the send button, the field loses the keyboard between press and release and gets it back after: a press slid off before release leaves it on the control, a composition under way in the field is cancelled, and a press on another tile's control moves the keyboard to that tile. If wrong: two controls less in the Tab order.
20. **The field's scroll is the kit's again.** A fix round had made it stick to its end, to keep a caret at the end in view when a chip lowers the cap on lines; that made a long draft jump to its end whenever the window came back. Taken out; the rare case is left: the caret can sit under the last visible line until the next key. If wrong: one line and its test.
21. **The queued strip counts its chips:** "Queued: TEXT · N attached", or "Queued: N attached" without text. The plan showed the first chip's name for a queue without text, and nothing for chips beside text. If wrong: wording.
22. **A new chip, and a chip whose answer is a problem, is scrolled into view, and the row fades at an edge that hides chips.** The row never wraps (decision 4), so a third chip in a narrow tile was out of sight. Rune's reveal ends other scroll holds in the window for that moment. If wrong: a few lines.
23. **A chip that is being read says "Reading…"** after its name. Before, only the tooltip said so and the send button was off for no visible reason. If wrong: one element.
24. **With no box focused, a paste takes an image also when text is beside it.** There is nowhere for the text to go. In a box the rule stays text first, as Jerod chose. If wrong: one flag.
25. **Smaller things the wave took:** the same path is not attached again while a message with it is queued; a pasted chip lets go of the clipboard's bytes once it is read; a drop checks again that its session takes a message; the decoder gets the memory budget that is left; the test that the program's input cannot lock waits for a marker and not for 300 ms; the live test prints "image and file sent" and "a 3 MB line went through" only when true. If wrong: each is a line or two.

## Left, each by a ruling

26. **When a send fails, or the program dies with the message, a pasted image cannot be had back.** The message stays in the conversation as sent, with "1 image"; its text can be copied from there. If wrong: a failed send gives its chips back to the box.
27. **Chips are not held to the 48 points of conversation.** Only lines of text give way. In the lowest tile with chips the conversation has about 12 points, and with a queued message none, so a permission request waiting there cannot be reached until the tile is made taller. Put to Jerod with ruling 14. If wrong: the box gives way to a waiting request as it does to the "open elsewhere" question.
28. **The live test prints counts, not shapes.** If the program stores a message with attachments in another form than the reader expects, the test says "0 file(s)" or "text kept whole: no", and someone must look at that one stored record by hand to correct the reader. If wrong: the test prints the block types and key names of its own session's record.
29. **The message field's inner key is `input`**, not `mr-…`, copied from the kit so that everything that finds the field still does. A departure from the plan's rule on keys, on purpose. If wrong: a rename and the tests that look it up.
30. **With the attach dialog open, a press that opens the folder dialog shows the toolkit's "already open" error**, and the other way round a line under the box. One dialog at a time is the toolkit's rule. If wrong: one flag shared by both.
31. **A typed message that ends in the form of an `Attached files:` block reads back, after a restart, as files.** The plan's own rule for the reader. If wrong: a marker the adapter writes that a person would not type.
32. **In a tile 172 points high and narrower than about 420, the "open elsewhere" question's buttons wrap and two are cut**, as before this plan. If wrong: a compact card.
33. **Small things left:** `write_line` copies each line once more; view tests wait for the worker threads by counting frames; turning orientations 5 to 8 copies the decoded image (about 1 GB at the pixel cap) and only orientation 6 is tested; no test at the pixel cap's edge, of bad base64, of `new_session` with chips, of stacked tiles taking a drop, of a paste while a dialog is open; `field::field` takes seven arguments by position; `glue::setup` makes the thumbnails' cache anew on every call; a thumbnail shows the middle of a wide image; a photo with a problem shows the file sign; the off send button of a tile with a problem chip looks like that of an empty box. If wrong: each is small.
34. **Everything the whole-branch review declined to judge stands as built**, twelve lines in its report. Those a user can meet: an image file over 32 MiB is refused and not sent by its path instead; HEIC, AVIF, BMP, TIFF, SVG and PDF go by path; a text paste into the box now makes the toolkit fetch the clipboard's image too, on its own worker; a drop veil could stay if the desktop sent no "left" event (X11 only). If wrong: each is its own small change.

## Sent pictures, after Jerod's first look

On 2026-11-16 Jerod pasted an image, saw that Claude answered about it, and named that the image itself was not shown in the conversation. Asked, they said "Yes, build it": a small preview in the message, for images sent now and for sessions opened again, no click to enlarge. It was built on this branch in two parts, each reviewed.

35. **One picture of 320 pixels serves the chip and the message.** One decode, one drawn picture, one id. If wrong: a second, larger picture for the conversation.
36. **A reopened session's pictures arrive after its history, each by itself, into slots of a fixed height.** The conversation neither waits for pictures nor moves when one comes. If wrong: nothing a user sees but a moment of outlined boxes.
37. **The row is 120 points high; a picture shows whole, 60 to 240 points wide; several scroll sideways.** The plan had no rule. If wrong: three numbers.
38. **The line "N images" is gone.** Every image has a slot, also one whose stored bytes cannot be read: it stays an outlined box with the photo sign. If wrong: the line comes back for those.
39. **Each stored image keeps its place.** The first shape let an unreadable image in the middle shift the ones after it; the seam now carries one entry per image, empty where the bytes could not be got. If wrong: nothing.
40. **A chip is prepared before a stored picture.** A session opened with many stored images must not hold up an image the user is about to send. If wrong: a few lines in the prepare thread.
41. **A press on a picture focuses its tile, leaves the keyboard where it is, and does nothing else.** As the first version was built it did not focus an unfocused tile. Seeing a picture large is left. If wrong: a later addition. (Jerod asked for it on 2026-11-16, after the merge: "being able to click an attached picture to open it". It goes into plan 7.)
42. **Left:** every picture of a loaded session stays in memory as a small picture (about 0.4 MB at most each) while the session is kept, shown or not; the window gathers every session's picture ids on each message from the backend, which grows with the pictures held and not with a conversation's length; pictures are made for a history answer that is then not used because the session was loaded meanwhile; the stored image block's shape was written by hand, and the live test's new line (`images with bytes the app could read: N of M`) settles it. If wrong: pictures made only for rows on screen; a corrected reader.
43. **The pictures row is nothing to a screen reader, and its pictures are images** named "Image N of M", or "Image N of M, not loaded". A first fix gave the row the role of a group, which the toolkit still announces as a button when it has a press handler; the re-review caught that the test read the wrong layer. The second fix was read and run by the controller and not reviewed again; its test reads the accessibility tree. The same pattern makes every tile and the right panel a button to a screen reader, which is older than this branch and left for a pass over accessibility. If wrong: a role on two elements.
